# Jira testing 状态变更 → 钉钉群通知（工作时段版）

## Context

现有 `examples/recipes/jira-watch/` 每 15 分钟拉一次 Jira「任何更新」并通知创建人/经办人。要改成**工作时段内每小时拉「状态变成 Testing 的 case」**，按业务规则通知：

| 谁把 case 改成 Testing | 通知谁 |
|---|---|
| 后端开发（components = `API-H5`） | @ 报告人（测试）+ @ **关联前端 case 的经办人** |
| 前端开发（components = `H5`） | @ 报告人（测试） |

后端开发本人不 @（他刚改完），同一人不重复 @。全链路脚本，不跑模型、不花 Token。

## 已核实的事实（2026-11-05 实测）

| 事实 | 值 |
|---|---|
| 监控的状态 | 只 `Testing`。`In Testing` 是测试人员正在测，不监控 |
| 「这一小时内变成 Testing」 | JQL `status CHANGED TO "Testing" AFTER <窗口>` 原生可用，支持 `-1h`/`-3d`/`"2026-11-04 18:00"` 绝对时间 |
| **JQL 的坑** | `CHANGED TO` 匹配**状态变更历史**不是 `updated`；返回里含「曾变成过、现在状态已变」的 case（CH-35453 现为「完成」）→ 必须再加 `status = "Testing"` 过滤当前状态 |
| case 确实会经过 Testing | CH-35452、CH-29410 变了 Testing 后变 In Testing。「当前是 Testing」= 测试还没领走 = 该通知；已被领走的不再通知 |
| 前端/后端区分 | components：`H5` = 前端，`API-H5` = 后端 |
| 关联 case | issue links，字段是 `outward_issue`/`inward_issue`；type 有 `Addresses`、`Blocks` |
| 配对规律 | 同一报告人（测试）建的 case 互相关联，一端 H5 一端 API-H5。实测 CH-35476(API-H5, Jane Long) ↔ CH-16861(H5, Lucy Jiang) |
| 关联 case 的经办人 | `outward_issue` 里没有 assignee，要再查一次 `jira_get_issue` |
| 当前 sprint | `sprint in openSprints()` 可用（39 条含 `-3d` 窗口）；`sprint` 字段取不到名字，按它过滤可用 |
| changelog | MCP 拿不到（include/fields/expand 都试过） |
| `updated` | 会被评论、sprint 变更（每两周）推高，不能当状态变更时刻；真正决定发不发的是 JQL 时间窗 |
| 节假日 | `https://holiday.ailcc.com/api/holiday/allyear/2026` 可用，365 天。`is_holiday === 0` 即工作日（自动含调休补班） |
| **补班日** | 2026 年 6 天调休补班落在周六周日（1/4、2/14、2/28、5/9、9/20、10/10），cron 的 `1-5` 会全部漏掉 → **cron 必须每天触发，由脚本判断** |
| 中台 cron | `kernel/cron.ts` 支持 5 段表达式（分钟/小时/日/月/星期），`*` 与 `1-5` 都能用；合盖醒来只补最近一次 → 「上一轮时间」要自己记文件 |

## 决策（已确认）

1. 后端 case → Testing：@ 报告人 + @ 关联前端 case 的经办人；前端 case → Testing：@ 报告人。后端开发本人不 @。
2. 关联 case：两种 link type 都看，只取 components 是 `H5` 的那个。
3. **cron 每天触发**（`0 9-12 * * *` + `30 13-17 * * *`），脚本查 `is_holiday` 判断今天干不干活：周末/法定假日安静退出，调休补班日照常跑。
4. **窗口 = 上次跑到现在**：脚本把「上次查到的时间」记在本地文件（`cursor.json`），JQL 用 `AFTER "<上次时间>"`。周末、节假日、电脑合盖都自然覆盖，不漏不重。
5. 接受重复发（`updated` 被评论或 sprint 变更推高时可能重发）。
6. 只监控 `Testing`。
7. 节假日：每年从 API 拉一次存本地；本地缺当年数据时脚本自己拉一次。
8. 前端 case 变 Testing 时不处理关联的后端 case。
9. 每个 case 一条消息，各自 @。

## 改动

### `examples/recipes/jira-watch/watch.ts`（改造）
- **工作日判断**：读 `holidays.json` 里今天的 `is_holiday`；为 1 → 安静退出（不发事件）。当天不在缓存里 → 先调 API 补当年数据再判
- **窗口**：读 `cursor.json` 的 `lastCheckedAt`（没有就用「昨天 18:00」），JQL 用 `AFTER "<该时间>"`；跑完把当前时间写回文件
- JQL：`project = CH AND sprint in openSprints() AND status CHANGED TO "Testing" AFTER "<窗口>" AND status = "Testing"`
- 命中后逐个 `jira_get_issue(fields 含 issuelinks)`，从 `outward_issue`/`inward_issue` 找 components 含 `H5` 的关联 case，再查一次拿其经办人
- 只对 components 含 `API-H5` 的 case 做关联查找（前端 case 不查）
- detail 增加 `linked_fe_key`、`linked_fe_assignee_*`、`components`
- 事件 id 保持 `KEY:updated`（中台去重）

### `examples/recipes/jira-watch/notify.ts`（改造）

- 正文首行是 @（紧贴手机号，钉钉要求），其后 case 号+标题、地址、状态、关联前端 case

## 已知限制（写进 README）

- 剩下 6 位后端开发没有手机号、也不在群里 → 涉及他们的 case 只 @ 报告人
- 测试人员在一小时内领走 case（Testing → In Testing）→ 该条不通知
- `updated` 被评论或 sprint 变更推高时，同一 case 可能重复发一次（接受）
- 节假日 API 拉不到时退回「周一到周五都算工作日」
- cursor.json 记录的是「上次查到什么时间」，删掉它会重查一遍（会重复发）
