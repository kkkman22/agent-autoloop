# 验收 Agent 接入自建 AI 团队：开发计划

## Context

现有团队跑在 agent-autoloop 上，流程是：飞书单聊 → `feishu-in.mjs` 转成 `im.message` → pm(codex,只读)派 `task.dev` → dev(zcode,yolo)实现 → qa(claude,只读)审查 diff。缺的是“操作真实产品、按验收标准逐项取证”这一环，而且验收标准传不到下游：资料文件只含本轮事件和本事项的 `decided`。

本计划在 qa 之后加一个独立的验收 Agent,由人在最后拍板。同时修三个现有问题：
- 事件 id 重复会被中台判重，直接丢弃(`kernel/decide.ts:263`):PLAYBOOK 固定用 `<subject>:dev`,返工时派出的 task.dev 会被静默丢掉；
- pm 第 5 步和规则对不上;
- `feishu-in.mjs` 不校验发送人。

已定决策：
- Q1 只改你的团队；
- Q2 串行，打回经 pm,最多验 2 次；
- Q3 验收标准写进 `tasks/<subject>/criteria.md`,pm 升到 `edit`;
- Q4 claude 加 Playwright MCP;
- Q5 证据存本地报告，关键截图发你飞书；
- Q6 Bitbucket 合并由你手动；
- Q7 结局记进 STATUS.md 台账；
- Q8 验收 Agent 给 `full`,跑你的账号；
- Q9 统一叫法；
- Q10 由 pm 指定环境，默认本地 dev 加公网测试 API;
- 团队目录仍是 ai-group,并 `git init`。

不改 agent-autoloop 仓库代码。

## 关键设计

**事件链与层数**(超过 8 层只记录、不派发):

飞书消息(0)→ task.dev-1(1)→ task.qa-1(2)→ task.accept-1(3)→ 验收不通过 → task.escalate(4)→ pm → task.dev-2(5)→ task.qa-2(6)→ task.accept-2(7)→ 再不通过 → task.escalate(8)→ pm 只能问你，并在 STATUS.md 写“待你决定”。

**事件 id**:`<subject>:<步>-<n>`。n 表示这是第几次开发，由 pm 每派一次加 1;下游的 qa、accept 沿用同一个 n;上报写成 `esc-<角色>-<n>`。

**criteria.md**:pm 派活前写好，派出后不再改；如需修改，只能由你通过 pm 改，并在文件末尾记一笔变更。格式如下：

```
# <subject>
需求:一句话
验收:要 | 免(原因)
环境:app=revision；起法=git worktree + pnpm --filter revision dev -- --port 19524 --strictPort；API=默认公网测试
A1 要验什么 | 怎么验 | 证据:截图/接口返回/日志
```

**STATUS.md 台账**:
- pm 派活时写“进行中”;
- 验收 Agent 收尾时写“已完结 <日期> 你批准”或“免验收已完结”;
- 第二次验收仍不通过，pm 问你时写“待你决定”。

**验收 Agent 每一轮的步骤**(写进 accept 技能):
1. 读 criteria.md。写着“验收：免”就只写 STATUS.md、发一条完结通知，然后结束。
2. 用 `git worktree add ~/code/work/ai-group/tasks/<s>/wt <提交>` 检出待验代码，执行 `pnpm install`。
3. 在 19524 端口起开发服务，和 dev 自测用的 9524 错开。
4. 用 Playwright MCP 按清单逐项操作，取证。
5. 登录：账号从 harness 的 `data/accounts.yaml` 读，界面登录卡住时用 `tests/utils/api_client.py` 的 `login_and_get_session` 直接拿 credential。还不行就把该项判“不确定”。
6. 报告写到 `tasks/<s>/acceptance/<n>/report.md`,截图放同一目录。
7. 关停服务，用 `git worktree remove` 删掉检出的目录。

技能里写死四条规矩：测试通过不算验收；没有证据判“不确定”;不验清单以外的东西；只返工没通过的项。还要写死：只碰测试环境和测试账号，不改代码、不提交；凭据和账号不进报告，也不进卡片。

**判定结果怎么走**:
- 全部通过：发 `ask` 卡片，逐项列结论和证据文件名，选项为“通过”(推荐)和“打回”,关键截图同时用 lark-im 发你飞书私聊。你点“通过”,它写 STATUS.md 并发完结 `notice`;你点“打回”,它把你写的原因放进 task.escalate 交给 pm。
- 有不通过项：直接发 task.escalate,detail 写明每项的问题，交 pm 裁决。
- 有不确定项：发 `ask`,选项为“我处理好了，重验”和“打回”。你回答后它在原会话里接着验，层数不增加。
- 判“不通过”和“不确定”都**不能**交 outcome failed,那会让中台自动重派。

**「验收」规则**:
- `when`:来源 feishu,类型 `task.accept`;
- `to`:accept,`cwd`:`~/code/work/ai-group`,`skill`:accept;
- `prompt`:“先读 .agent/PLAYBOOK.md 的「验收」节，照做。”;
- `parallel: 1`:按 subject 分事项，同时只跑一个，避免端口冲突；
- `timeout: 60`(分钟);
- `emits`:feishu 来源的 `task.escalate`;`channels`:feishu。

**PLAYBOOK 各节的改动**:
- pm:开工先看 STATUS.md,已完结就交“没事可做”;派活写 criteria.md 和 STATUS.md;来自验收的 escalate 和 qa 的同样裁决；第二次验收不通过就问你；删掉第 5 步。
- dev:读 criteria.md,不得修改;交 task.qa 时写明分支、提交和 criteria 路径。
- qa:对照 criteria.md 审查；通过交 task.accept,不再交 task.report。
- 回执格式：加上 `task.accept` 类型和新的 id 规则。

## 执行步骤(按顺序)

**P0 底座与安全**
1. 备份 `rules.json`,存成 `rules.json.<时间>.bak`。
2. 在 ai-group 执行 `git init`,写 `.gitignore`(忽略 `tasks/`),把现状提交一次。
3. 修改 `feishu-in.mjs`:发送人不在白名单内就记日志并忽略，查进度的回复也按白名单过滤。在 `.feishu-in.env` 加 `FEISHU_ALLOWED_SENDERS=ou_ad50627fb84c4d52c8c655ddf33dd778`,再用 launchctl kickstart 重启守护进程(从 plist 读出 label)。

**P1 浏览器**
4. 执行 `claude mcp add --scope user playwright -- npx @playwright/mcp@latest --headless --output-dir ~/code/work/ai-group/tasks/.playwright`。
5. 冒烟测试：在 ai-group 下用 `claude -p --permission-mode bypassPermissions` 打开 example.com 并截图，确认能出图。

**P2 文档**
6. 写 GLOSSARY.md、TEMPLATE-criteria.md,改 PLAYBOOK 四节并新增「验收」节。

**P3 技能**
7. 写 `~/.claude/skills/accept/SKILL.md`。确认 `data/accounts.yaml` 是否存在(只看文件在不在，不读内容);不存在就请你填一份测试账号文件，权限设为 600。

**P4 接线(放在最后)**
8. 修改 `rules.json`。
9. 执行 `agent-autoloop check`,再用 `rules explain feishu task.accept` 确认派给「验收」,用 `rules explain feishu task.qa` 确认派给「审查」。

**P5 演练**
10. 验证去重：用一个没有规则接的类型 `drill.ping` 发事件，同一个 id 发两次应当判为重复；换成带新序号的 id 应当被接收，证明新的 id 方案有效。
11. 单独演练验收：手写 `tasks/drill-20261109/criteria.md`(A1:revision 登录页能打开并截图),用 `agent-autoloop emit task.accept --key <来源密钥> --subject drill-20261109 --id drill-20261109:accept-1` 触发，检查报告和截图是否落盘、飞书卡片是否到达；点“通过”后检查 STATUS.md 是否写了“已完结”,worktree 和服务是否都已清理。
12. 全链真实小任务：通过飞书发一个小需求，看完整链路。你在验收卡片上打回一次，确认 `task.dev-2` 能正常派出(不被去重吞掉);之后通过。

**P6 收尾**
13. 更新计划文件，提交 ai-group,向你汇报演练结果和遗留问题。

## 验收标准

- `agent-autoloop check` 通过，路由符合上面的设计。
- 非白名单账号私聊机器人不会产生事件，日志中有忽略记录。
- 后台运行的 claude 能用 Playwright MCP 截图。
- 第 11 步：报告、截图、卡片、STATUS.md 都齐全，worktree 已删除，19524 端口已释放。
- 第 12 步：经过一次打回后 `dev-2`、`qa-2`、`accept-2` 都被派出，通过后 STATUS.md 写明已完结。
- `tasks/` 下的内容不进 git,报告和卡片里没有出现账号密码。

## 回滚

- 规则：用 P0 的备份恢复 `rules.json`。即使规则改错，中台也会继续按旧规则运行，并发卡片提醒。
- PLAYBOOK、feishu-in:在 ai-group 里 `git revert`。
- 浏览器：`claude mcp remove playwright`。
- 技能：删除 `~/.claude/skills/accept`。
