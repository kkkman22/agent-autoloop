# 日志增长与投影重建

事实日志是唯一的权威状态，只追加，不压缩。这份说明写清它长大以后会发生什么、现在做了什么、归档要满足哪些条件才能做。它不改协议；涉及协议的地方单独标出。

## 现在的数字

Apple M5 Pro、Node 24.21.0，`node scripts/history.ts 1000 10000 100000` 灌出约 110 万条事实（10 万轮完成的任务）后：

| 项目                         | 实测      |
| ---------------------------- | --------- |
| 正常启动（复用投影）         | 83.6 ms   |
| 从日志整份重建投影           | 36.2 s    |
| 空闲 RSS                     | 114 MB    |
| 领活、交结果等单个请求中位数 | ≤ 0.72 ms |
| `GET /v1/state` 中位数       | 688 ms    |

正常启动和单个请求不随历史变慢：投影和索引按需读取，内存里不放全部历史。随历史线性变慢的原来有两处：整份重建，和 `/v1/state`、`/v1/metrics` 里对全部轮次的汇总；两处下面都处理了。磁盘占用随历史一直增长。

## 不变的约束

- 投影随时可以丢掉、从日志重建；重建不重新执行规则，不改旧事实，不写数据迁移。
- 判断、追加事实和更新投影在同一个事务里提交。
- 格式指纹（`host/fingerprint.ts`）一变就重建；指纹对不上只意味着第一次启动慢，不意味着丢数据。
- `why` 和 `/v1/stream?after=0` 能读到每一条事实。这是协议的一部分。

## 已经做的：重建可以接着做

以前整份重建在一个事务里完成：110 万条事实要 36 秒，中途被杀就回滚，下次从第一条重来。日志再长一些，一台总被看门狗重启的机器可能永远重建不完。

现在每 5 万条事实提交一次（`kernel/store.ts` 的 `REBUILD_CHUNK`）。检查点就是现有的 `projection_meta`：做的过程中格式记成 `building:<指纹>`，序号是已经提交到的那一条；只有最后一批把格式改成正式指纹。

- **中途被杀**：已提交的批次留着，下次 `openView` 看到 `building:<本机指纹>`，从记下的序号接着做。`tests/rebuild.test.ts` 用真实进程在重建中途 `SIGKILL`，再核对接着做完的投影和一次做完的完全一致。
- **别的格式的半成品**：不接着用，从头重建。不同版本的 `evolve` 写出的行可能不一样。
- **重建开始前打开的视图**：`commit` 除了核对日志序号，还核对投影格式，对不上就拒绝，事实不会落到做了一半的投影上。
- **进度**：日志超过一批时，`host/runtime.ts` 在标准错误输出里写“正在从日志重建视图：已做 / 总数”；`/v1/metrics` 的 `hub_projection_seq`、`hub_projection_format_matches` 在重建前后也能看出来。中台在重建完成前不监听端口，所以重建当中只能看日志输出。

代价：一次整份重建多出约 20 次提交，相对 36 秒可以忽略。基准要在下一次跑 `scripts/history.ts` 时补上分批后的重建耗时。

## 还要测量的：`projection_refs` 和 `why`

`projection_refs` 为每条事实里改到的每个事件、轮次、卡片记一行（集合、键、序号），供 `why` 和卡片查找按记录定位事实。它和事实一样随历史线性增长。

要测量的是：110 万条事实时 `projection_refs` 的行数和占用的字节，`GET /v1/runs/<id>/why` 对最早、最近和事件最多的那一轮的耗时。`why` 只按主键前缀查，预期不随历史变慢；如果实测变慢，先查索引，再考虑保留策略。没有数字之前不加保留策略。

## 已经做的：汇总不扫全部历史

逐项测量（1.5 万轮、6 万条事实，`/v1/state` 一次 196 ms）：

| 查询                            | 耗时     | 随什么增长   |
| ------------------------------- | -------- | ------------ |
| 等回答的卡片                    | 136 ms   | 开着的卡片数 |
| 按规则、Agent、状态分组汇总轮次 | 46 ms    | 全部历史     |
| 最近结案的卡片                  | 17 ms    | —            |
| 数全部事实（`/v1/metrics`）     | 16 ms    | 全部历史     |
| 其余（今天完成、翻页、在线等）  | ≤ 0.5 ms | —            |

测量脚本让每一轮都提问，所以开着 1.5 万张卡片；正常使用里开着的卡片很少，这一项不随历史增长。随历史线性增长的是分组汇总和数事实，按 46 ms 推算，10 万轮约 300 ms；`/v1/metrics` 每次被抓都要做一遍，会占住中台唯一的线程。

现在 `evolve` 在每次改到一行轮次时，先按旧行减一份、再按新行加一份，结果存在单独的派生表 `projection_tallies` 里：它和 `projection_pending`、`projection_refs` 一样不算业务记录，不出现在快照和查询视图里，重建时一起清空重算。按规则、Agent、状态各一行，记轮数、重试中的轮数、输入和输出 Token、费用。费用按十亿分之一存成整数，加了再减回去正好是零，不留浮点零头。“今天完成几轮”和日期有关，不预先累加，按 `finished_at` 的索引只读今天的。`/v1/state` 和 `/v1/metrics` 共用 `kernel/state.ts` 的 `countsOf`。数事实改成读最大序号：序号从 1 起连续，最大序号就是条数。

它和其他投影一样从日志重建；`tests/tallies.test.ts` 把它和逐行扫描的结果在完成、失败重排、合并删除、停止、跨天和重建之后逐一核对。这改了 `kernel/evolve.ts`，格式指纹随之变化，升级后第一次启动会重建一次视图。

## 归档：设计，暂不实现

归档的目的是让 `hub.db` 不再无限长大。只有下面几条都有测试和一次恢复演练之后才做：

1. **检查点可验证。** 在序号 S 处写一份检查点：投影快照的 SHA-256、S、以及 S 之前全部事实的哈希链末端。任何时候都能用“归档文件 + 剩下的日志”重放出同一个快照哈希，对不上就拒绝使用这份检查点。
2. **归档可恢复。** S 及以前的事实整批移进 `archive/facts-<起>-<止>.db`，和备份一样带清单（大小、SHA-256、条数）。`hub.db` 只留 S 之后的事实和检查点。启动时从检查点开始重建，而不是从第一条。
3. **可以回滚。** 把归档文件的事实原样插回 `hub.db`、删掉检查点，就回到没归档的样子；回滚后整份重建的快照必须和归档前一致。
4. **协议照旧，否则写明。** `why` 和 `/v1/stream?after=0` 要能读到归档里的事实：要么按需打开归档文件，要么在协议里明确写“归档前的事实只在归档文件里”，并在 README 的“这次改了什么”里说明。后一种是不兼容改动，要单独决定。
5. **备份带上归档。** `agent-autoloop backup` 的清单要包含归档文件，`restore` 一起核对。

这一阶段做了可以接着做的重建和不扫历史的汇总。归档、检查点和保留策略都没有实现。
