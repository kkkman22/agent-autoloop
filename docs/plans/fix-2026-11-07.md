# 审核修复计划(2026-11-07)

来源:2026-11-06 全面架构审核(基线 main@6310d90)。每个工作包先写复现失败方式的测试,再改实现。

## 工作包

- **F1 插件签名按点名标签验证**:`add --ref v1.2.0` 时验的是 `git describe` 选中的同提交另一枚标签,未签名版本被放行。改 `cli/plugins.ts addPlugin`:验 `--ref` 点名的那枚;无 `--ref` 时验实际检出的最新标签。测试 `tests/plugins-cli.test.ts` 已红,即失败方式。
- **F2 签名测试 fixture 两处错**:`picky` 仓库没建标签(209 行的拒绝理由错);207 行把私钥当公钥登记。修 fixture;probe 密钥改放进每次运行独立的 scratch 目录,不再污染 `$TMPDIR` 导致测试静默跳过。
- **F3 回答正文长度上限**:`kernel/decide.ts answer()` 只验类型不验长度,1MB 回答可进卡片与下一轮上下文;同类入口 tell 限 2000、回执限 4000。回答文字上限 4000(与 ask/notice 正文一致)。先在 cards 测试加 4001 字被拒、4000 字通过的失败测试。协议文档同步。
- **F4 指定回答者的卡片,链接不能答**:`answerByLink` 以 `by:"链接"` 跳过卡片 answerers,规则限定谁可答时被绕过。链接证明不了是谁:卡片带 answerers 名单时拒绝链接回答(403),在通道里答。先在 http 测试加失败用例。协议文档与 SECURITY 同步。
- **F5 GitLab 流水线按来源过滤**:`gitlab.ts checks()` 只按 sha 查,同 sha 的 API/trigger 流水线可冒充检查通过;GitHub 侧过滤 `event=pull_request`。GitLab 侧补 `source=merge_request`(shipRuns 对齐 push)。先在场景表加「同 sha 的非合并请求流水线不算数」,GitLab 方言下红。
- **F6 Ship 设置的基点**:`action.ts` 读 `${target}^`,一次 push 含 merge+后续提交时读到合并后设置。改为:push 范围内最老的 merge 提交的第一父(= 合并前 main);无 merge 时仍 `target^`。先在 delivery-action 测试加失败用例。
- **F7 waitLive 活性**:merged 自己的 Ship 失败、后续纯文档 Ship 成功且 live 已含 merged 代码时,交付永远报「发布没有通过」循环重试。live 包含 merged 代码即视为已发布。先在 delivery 测试加失败用例。
- **F8 适配器错误与验签错误分开**:签名过了但事件内容不合法,现在也回 401「验签没过」,掩盖配置故障。验签失败仍 401;签名通过后适配/解析失败回 400 带原因(调用方是已验签来源,可说真话)。先在通道测试加失败用例。
- **F9 fixtureClear 挪出生产模块**:`host/runtime.ts` 的测试辅助绕过日志改投影。移到 `tests/storage.ts`(它本就只放 fixture 清理);`reloadRules` 里直接读 `current` 的地方改走 `getView()`。
- **F10(执行中发现)jira-watch 测试依赖真实日历**:周一起到周五的值守逻辑让测试在周末静默退出、找不到日志。全量验证时撞上周六暴露;干净 main 同样挂,与本次修复无关。给 `jiraWatch` 夹具补默认的固定工作日 `now`(日历相关测试本就自己注入,不受影响)。
