# agent-autoloop 深度评审与后续 Roadmap

- 日期：2026-11-04
- 审核基线：`main @ 43f681b`
- 审核性质：只读评审，未修改仓库代码
- 审核视角：高级技术经理，重点看代码安全与架构合理性；高级产品经理，重点看功能实用性
- 说明：本文不是协议文档，不改变任何既有约定

## 结论摘要

这是一个工程质量明显高于同类个人自动化项目的系统。内核的事件溯源、决定与提交同事务、协议与插件分离、审批卡和测试强度都成立。但它当前的默认安全边界是“一台电脑、一个用户、所有插件和 Agent 都可信”。一旦启用自动交付、远程 worker 或多人通道，这条假设就会被打破。

产品上，它解决的是“让 Agent 在你不在时干活，关键处停下来问你”。这个定位清晰且有差异化。短板在规则生命周期、可观测性、成本控制和运维闭环。

## 1. 审核范围与验证

本轮为只读审核，没有修改仓库文件。阅读了协议、内核、宿主、worker、插件、CLI、测试、模拟和 CI 配置，并用 `/tmp` 下的探针复现了关键问题。

| 检查 | 结果 |
|---|---|
| 完整 `npm test` | 302 项，301 通过，1 跳过，未安装 fish |
| 内核变异测试 | 25 个变异全部被抓住，0 存活 |
| `npm run typecheck` / `format:check` | 通过 |
| 运行环境 | Node v24.22.1，运行时依赖为空 |
| 未单独验证 | nightly 的 1000 次 SIGKILL、性能基准、真实 Claude/Codex/飞书/交付脚本 |
| 仓库外信息 | 分支保护、CODEOWNERS、线上部署配置无法从代码确认 |

测试强不代表安全边界完整。下面的问题大多不是内核算法错误，而是配置默认值、信任边界和自动化链路的问题。

## 2. 安全性评审

### 高优先级

1. **通道回答者校验默认放行，未登记通道也能收卡回答。**
   - 证据：`kernel/decide.ts:387` 用 `if (allowed && ...)` 把缺失的 `answerers` 当成放行。探针里，一个没有名单的通道，以及一个根本没在 `rules.channels` 登记的通道，都能收卡并以任意 `by` 回答，返回 `changed:true`。
   - 影响：IM 群里的任何人都能替你做删除、停服、花钱的决定。
   - 修复：通道必须在 `rules.channels` 登记；`answerers` 缺失或为空默认拒绝；只有显式 `"*"` 才允许所有人；在 `parseRules` 阶段报错；补缺失名单、未登记通道、空回答者三类回归测试。

2. **PR 能改写 CI 范围脚本，让必需检查空转。**
   - 证据：`.github/workflows/check.yml:30` 在 PR 的合并提交上执行 `scripts/ci-scope.sh`。PR 把这个脚本改成输出 `scope=docs`，所有测试步骤都会跳过，必需检查仍然是绿的。PR 也可以直接修改测试。
   - 影响：对启用自动合并的仓库，这是绕过全部质量门禁的路径。
   - 修复：范围脚本使用 base 分支版本；PR 至少跑 quick；改动 `.github/**`、`scripts/**`、`tests/**`、`package-lock.json` 强制 full 并要求人工批准；把这些路径设为受保护路径。

3. **自动交付把 PR 自己的 check workflow 当作可信门禁。**
   - 证据：`plugins/delivery/delivery.ts:41` 的 `fullCheck` 按 head SHA 找名为 `check` 的 workflow run，并信任它的成功结果。同一仓库的分支，尤其是 Agent 自己推的分支，可以改 `.github/workflows/check.yml` 让这个 job 空跑通过，交付插件看到成功就自动合并。
   - 影响：在自动合并链路上，CI 不是可信门禁。LLM 审查只能作为建议，不能作为安全边界。
   - 修复：check workflow 的定义必须来自 main 的受保护版本；PR 触碰 CI、测试、`ops/delivery.json` 时禁用自动合并，转人工；或者用固定的 `workflow_run` 校验。

### 中优先级

4. **规则目标用原型链判断，错误配置会静默搁置工作。**
   - 证据：`protocol/rules.ts:36` 的 `isKeyOf` 用 `value in table`，会接受 `constructor`、`toString`、`__proto__`、`hasOwnProperty`。探针里 `to:"constructor"` 通过校验并解析到 `Object`，事件进入一个没有 worker 能领取的队列，也没有离线通知。
   - 影响：一个拼写错误或恶意规则可以静默吞掉工作。
   - 修复：改用 `Object.hasOwn`；ID 只允许小写字母、数字和短横线；显式拒绝保留字；补校验测试。

5. **删除或改名规则会静默搁置排队轮次和已回答卡片。**
   - 证据：`kernel/decide.ts:96` 的 `assignQueued` 在规则找不到时直接返回，`kernel/decide.ts:402` 的 `answer` 对找不到规则的卡片只记录 `routed: []`。
   - 探针结果：

     ```text
     queued after rule removal: [{ id: 1, state: "queued", rule: "r" }]
     claim after removal: null
     answer after removal: {"changed":true,"state":"decided"}
     run events after answer: [{ id: 2, routed: "[]" }]
     ```

   - 影响：用户只是在 `rules.json` 里删了一个规则，旧活和回答就静默消失。对普通用户，这比任何性能问题都更伤信任。
   - 修复：规则变更时扫描 queued run 和 open card，生成“规则已删除，这一轮不再执行”的通知并取消或关闭；或者保留旧规则版本直到相关 run 清空；回答时规则不存在返回 409。

6. **Ship 判定读取 target 的交付设置，不是合并前 main 的设置。**
   - 证据：`plugins/delivery/action.ts:21` 用 `target` 读 `ops/delivery.json`。一个 PR 可以同时修改设置和路径，让自己的 Ship 判定把改动当成内部变更。
   - 影响：这削弱了 `AGENTS.md` 要求的“设置只来自 main”。
   - 修复：Action 固定读取受保护的 base 或合并前 main 设置；`ops/delivery.json` 单独审查并纳入受保护路径。

### 中低优先级

7. **卡片链接只在提交回答时检查 7 天过期。**
   - 证据：`kernel/http.ts:97` 的 `cardAtLink` 在 GET 时直接渲染卡片，只有 POST 回答才检查过期。
   - 影响：链接进入聊天记录、代理日志或浏览器历史后，过期仍能看到卡片正文。
   - 修复：GET 也检查过期，返回 410 或只显示“链接已过期”；高风险卡片考虑一次性链接。

8. **密钥和 Agent 默认同用户，没有文件隔离。**
   - 证据：`host/runtime.ts:23` 只在首次创建 `master.key` 时设 0600，已存在文件不纠正权限。`host/up.ts:31` 加载 `secrets.env` 没有权限检查。`hub.db` 依赖 HOME 0700。Agent 以同一 OS 用户运行，`worker/worker.ts:94` 还把 `AGENT_AUTOLOOP_HOME` 传给它。
   - 影响：文档承认这是边界，但默认部署没有隔离。提示注入可以读到主密钥、数据库和适配器密钥，绕过“Agent 看不到密钥”的边界。
   - 修复：启动时校验并修正权限；worker 使用独立用户或容器；Agent 环境不传 HOME，只给 run 目录；把主密钥移出 Agent 可读目录。

9. **worker 对 401 直接丢弃结果，主密钥轮换没有排空流程。**
   - 证据：`worker/worker.ts:407` 的 `settle` 对 4xx 一律删除 `entry.json`，包括 401。主密钥轮换后，正在跑完的 run token 失效，结果被丢掉，只留一行日志。
   - 影响：已经完成的活可能丢失，而且用户很难知道发生了什么。
   - 修复：401/403 保留结果并重试或告警；区分永久拒绝和临时鉴权失败；提供主密钥轮换的排空步骤和文档。

### 低中优先级

10. **MCP 把本人权限的写操作暴露给 Agent。**
    - 证据：`cli/mcp.ts` 向 Agent 暴露 `answer`、`resolve`、`stop`、`emit`、`tell`，只有工具注解，没有确认。
    - 影响：事件文本里的提示注入可以让 Agent 停止别的轮次、发事件或回答卡片。
    - 修复：MCP 默认只读；写工具显式开启；高危操作要求本人确认或独立 token。

11. **网络面还有三处低成本加固。**
    - `join` 接受任意 URL，没有拒绝 `http://`，worker key 会明文传输。
    - `readText` 先读最多 8MB 才抛 413，请求体限流不够早。
    - 长轮询和每密钥请求没有上限。
    - 影响：远程部署时存在中间人、内存和连接耗尽面。
    - 修复：非 loopback 强制 https 或 SSH 隧道；超过 1MB 立即中止；增加每密钥并发和速率上限；反向代理层也限流。

### 低优先级

12. **`tell` 文本上限与通道能力不匹配。** `kernel/http.ts:129` 允许 20000 字，但企业微信模板上限 2048 字节，Discord 2000 字符。超长文本会一直重试到放弃。修复：按目标通道能力分段或拒绝；`status` 显示投递失败。

13. **CLI 原样打印不可信文本。** `status` 和 `why` 会打印 Agent 写的卡片标题、正文和事件摘要。ANSI 或 OSC 控制序列可以修改终端标题、清屏或写剪贴板。修复：输出前剥离控制字符；只在 `--raw` 下保留原样。

14. **`delivered` 接受超前版本号。** `kernel/decide.ts:539` 存 `Math.max(delivery.version, version)`，不校验 `version` 不超过 `card.version`。一个通道上报未来版本后，卡片真实更新时会被当成已送达，更新被吞掉。修复：拒绝大于当前卡片版本的报告。

15. **文档与默认值有偏差。** `ASK_FIRST` 实际有 7 项，README 和协议示例只列了删除数据、停服、花钱、对外发消息 4 项。协议示例中的 JSONC 注释不能直接喂给只收 JSON 的解析器。修复：统一默认值和文档；要么支持 JSONC，要么把示例改成纯 JSON。

## 3. 架构评审

### 3.1 做得好的地方

- **内核边界不是口号。** `decide`、`evolve`、`commit` 的职责清楚，内核不读时钟、随机数、环境或文件。事实日志是唯一权威，投影可以在同一事务内重建。`tests/purity.test.ts` 把这条边界守住了。
- **协议是产品。** 六个门、密钥种类、能力 token、卡片链接、长轮询和流式日志都有明确约定。插件放在 `plugins/<名字>/{agent,channel,source}.ts`，内核不导入插件，产品名没有进入内核。
- **审批卡是真正的产品原语。** Agent 提问后结束这一轮，中台等待回答，回答再唤醒原事项，保留会话和上下文。这个设计同时解决了“不烧 token 地等人”和“人只看关键选择”两个问题。
- **测试是资产。** 20 万步固定种子模拟、8 的阶乘规模的有界穷举、SIGKILL 崩溃恢复、投影失败回滚、慢订阅者只读一条事实、卡片页面转义，这些都不是普通项目会做的。25 个内核变异全部被抓住，说明测试不是摆设。
- **交付审查的隔离思路正确。** 用裸 Git 对象生成快照，不 checkout、不跑 hooks、不做 textconv，Codex 在只读沙箱里审查，发布后再做健康核实。设计意图是好的，问题在信任链的上游。

### 3.2 结构性风险

- **单进程、单数据库、单写者。** 对个人自用是优点，对团队和 HA 是天花板。`node:sqlite` 仍是实验 API，Node 24 是硬门槛，升级 Node 需要重新验证。
- **日志只增不减。** 状态查询按历史扫描，项目自己记录的基准是：

  ```text
  110 万条事实时，状态查询约 927ms。
  ```

  随着使用时间增长，`state`、`spending`、`projection_refs` 会成为第一批运维痛点。现在没有 compaction、checkpoint、按日物化聚合，也没有 WAL 感知的备份命令。
- **规则不是一等公民。** 规则是 JSON 文件，没有安全的删除、改名、禁用、解释和试运行流程。版本只固定在 run 上，规则被删除后没有清理路径。这既是架构问题，也是最大的产品体验缺口。
- **信任边界默认是“单用户可信机器”。** 通道插件在 hub 进程内运行，插件是可信代码，Agent 和 hub 同用户，交付自动合并又信任 PR 自己写的 CI。这个模型在个人电脑上自洽，在远程 worker、多人通道和自动合并场景下不自洽。
- **交付链路复杂度高。** `gh` 命令、GitHub API、LLM 审查、CI 等待、健康核实、自动合并回读，任何一环都需要真实仓库和权限才能验证。LLM 审查有提示注入和漏报风险，不能当安全门禁。
- **可运维性偏弱。** 没有指标端点、告警、备份恢复命令、发布标签和回滚流程。`update` 直接拉 main，格式指纹变化会触发全量重建，主密钥轮换会让卡片链接和 run token 失效。这些都需要在“能长期跑”之前补齐。
- **测试有盲区。** 真实 Claude、Codex、飞书和交付脚本没有在 CI 中运行。内核测试很强，宿主、插件和异常路径的覆盖相对弱。

## 4. 产品评审

### 4.1 定位

一句话：给会用 CLI Agent 的人，一个本地运行、事件驱动、能在关键处停下来问你的自动化中台。

它不替代 n8n、Zapier 的集成库，也不替代 GitHub Actions 的仓库 CI。它替代的是 cron 加脚本加人肉盯 Agent 的组合。

### 4.2 真实价值

- **暂停不烧 token。** Agent 提问后结束，中台等待，回答后唤醒。这是很多 Agent 调度器没有解决好的问题。
- **Agent 无关。** Claude Code、Codex、ACP、任意命令都能接，用户不被单一模型绑定。
- **本地优先、零运行时依赖。** 数据、密钥、日志都在自己的机器上，适合对隐私敏感的个人和小团队。
- **审批在聊天里完成。** 飞书、桌面通知、Webhook、卡片链接覆盖了不同通道能力。
- **审计链路完整。** `why` 和 `/v1/stream` 能还原一轮发生了什么，事件溯源在这里不是学术设计。
- **GitHub 交付是亮点。** 审查、检查、合并、Ship、健康核实是一条完整的开发闭环，不只是“定时跑个脚本”。

### 4.3 主要产品缺口

1. **规则生命周期是最大的可用性缺口。** 现在编辑 `rules.json` 是主要配置方式，没有安全的删除、改名、禁用、解释和试运行。删除规则会静默搁置排队工作和已回答卡片。建议把规则变成一等对象：`rules edit`、`rules validate`、`rules explain`、`rules disable`、`rules diff`，删除时自动取消并通知孤立工作。
2. **通道路由和审批角色不足。** 一个 hub 基本对应一个受众，没有按规则路由到不同通道、不同群、不同值班人，也没有角色和权限分级。多团队、运维告警、财务审批混在一起时会互相打扰，隐私边界也不清楚。建议增加规则级 `channels`、安静时段、严重级别和回答者角色。
3. **可观测性不足。** 现在主要靠 `status` CLI。卡片投递失败、通道放弃、规则最近失败、每规则成本趋势都不够直观。建议提供 `/metrics` 或结构化状态接口，并做一个仓库外的参考客户端，不要把总览页塞回内核。
4. **成本治理不足。** 重试 10 次会停，但单个 run 仍可能很贵，没有按规则、按天、按任务的预算和预警。建议增加预算上限、超预算暂停和成本卡片，至少让用户知道“这个规则今天花了多少”。
5. **运维闭环不足。** 备份、恢复、主密钥轮换、发布标签、升级回滚、Windows 和容器部署都没有形成产品化路径。安装体验不错，但“跑三个月不出事”和“出事后能恢复”还没有被认真覆盖。
6. **上手门槛仍高。** Node 24、飞书应用配置、Skill 复制、规则 JSON、GitHub 交付配置，对目标用户之外的人仍然偏难。`try` 是好的开始，但还需要一个十分钟内能收到第一张卡片的引导路径，以及不依赖真实飞书的本地演示通道。
7. **生态还很小。** 插件通过 `git clone` 安装，没有版本、签名、更新和兼容性声明。对个人项目可以接受，对生态是瓶颈。建议先做插件版本清单和签名校验，不要急着做市场。
8. **团队能力缺失。** 多租户、RBAC、SSO、审计导出、配额都不在现在的模型里。这不是内核应该立刻补的，而是独立的产品线。当前定位应该明确为个人和极小团队，而不是企业平台。

### 4.4 竞争与边界

它的护城河是“本地运行、Agent 无关、审批在聊天里、事件日志可审计”，不是集成数量。不要跟 n8n 比连接器，不要跟 GitHub Actions 比仓库 CI，也不要跟通用工作流引擎比画布。

“没有界面”是一个有效的架构约束。中台只提供口子，客户端由别人做，这个方向值得坚持。但需要一个官方参考客户端来证明这些口子够用。参考客户端应该独立仓库，使用 `/v1/state` 和 `/v1/stream`，不要进入 `kernel/`。

产品节奏上，先服务好“一个技术人管理几台机器和几个 Agent”的场景。团队版可以以后做，但不能在现在把内核改造成多租户系统。

## 5. Roadmap

### 5.1 排序原则

先修安全边界，再补可运维性，最后做产品化。每一阶段都保持内核只收、只分、只派、只记；不新增运行时依赖；协议变更先改 `docs/protocol.md` 和兼容说明；不做数据迁移，用新的事实表达状态变化。

### 5.2 阶段 0：止血，1 至 2 周

- **通道默认拒绝。** 通道必须在规则中登记，`answerers` 缺失或为空默认拒绝，只有显式 `"*"` 才放行。补缺失名单、未登记通道、空回答者三类测试。
- **规则生命周期。** 规则变更时扫描 queued run 和 open card，取消并通知孤立工作；回答不存在的规则返回 409；补删除和改名测试。
- **交付链信任。** CI 范围脚本从 base 分支读取；PR 至少跑 quick；改动 CI、测试、交付设置强制 full 并转人工；`fullCheck` 和 Ship 设置从受保护的 main 读取；保护 `ops/delivery.json`。
- **网络和密钥小修。** 卡片链接 GET 检查过期；请求体超过 1MB 立即中止；非 loopback 拒绝明文 HTTP；启动时修正 `master.key`、`secrets.env` 和 `config.json` 权限；worker 对 401 保留结果；MCP 默认只读。
- **输出和输入边界。** `tell` 按通道能力拒绝或分段；CLI 剥离控制字符；`delivered` 拒绝超前版本；统一 `askFirst` 文档和默认值。

验收标准：每个修复先有失败的回归测试；`npm test`、`npm run typecheck`、`npm run format:check` 全绿；不引入运行时依赖；协议文档同步更新。

### 5.3 阶段 1：可运营，3 至 6 周

- **备份与恢复。** 提供 `backup` 和 `restore`，使用 SQLite 备份接口，明确 WAL 和主密钥的处理；写一次恢复演练文档。
- **可观测性。** 增加结构化指标和健康检查，暴露每规则成本、失败率、投递失败、投影重建进度；提供按日聚合，避免每次查询扫描全部历史。
- **限流与隔离。** 每密钥并发和速率上限；长轮询上限；通道异常重启加退避；worker tick 的异常隔离；把通道插件崩溃对 hub 的影响降到最低。
- **日志增长。** 设计 checkpoint 或归档方案，保持事实日志权威；给投影重建加进度和可恢复状态；对 100 万级事实做基准。
- **发布工程。** 打语义化版本标签，提供 `update --check`、升级说明和回滚；CI 保护路径；增加 24 小时 soak 和故障注入测试。

验收标准：完成一次真实恢复演练；百万级事实下状态查询达到可接受延迟；升级和回滚各演练一次；CI 能阻止改动测试和交付设置的 PR 自动合并。

### 5.4 阶段 2：产品化，6 至 12 周

- **规则编辑体验。** `rules edit`、`validate`、`explain`、`disable`、`diff`；支持 JSONC 或提供纯 JSON 模板；规则变更前展示“会影响哪些排队工作和卡片”。
- **路由与审批角色。** 规则级通道、安静时段、严重级别、回答者角色；卡片链接一次性或短时有效；按规则的成本预算和超预算暂停。
- **参考客户端。** 独立仓库做一个总览页，使用现有协议读取状态和流；移动端优先，展示待回答卡片、最近失败、每规则成本和投递状态。内核不加界面。
- **插件生态。** 插件版本、签名、兼容性声明和更新命令；worker 独立用户或容器运行的安装选项；Windows 通过 WSL 或容器给出明确支持路径。
- **交付扩展。** GitLab 或其他代码托管；受保护路径策略；人工审批门；把 LLM 审查定位为建议而不是门禁。
- **文档与本地化。** 英文协议和运维文档补齐；十分钟快速开始；真实场景 recipes 增加失败恢复和成本控制示例。

验收标准：新用户在十分钟内通过本地假通道收到第一张卡片；内核中没有产品名和界面；协议兼容性测试通过；至少 3 个真实用户完成试用并给出反馈。

### 5.5 不建议现在做

- 不要把总览页、工作流画布或大屏放进 `kernel/`。它们应该是外部客户端。
- 不要为了团队功能把多租户、RBAC、SSO 塞进内核。团队版是独立产品线。
- 不要为了方便引入运行时依赖。Node 24 自带能力是当前架构的重要优势。
- 不要承诺 exactly-once。保持 at-least-once，把幂等责任写进 Skill 和示例。
- 不要让自动合并信任 PR 自己写的 CI。触碰 CI、测试、交付设置的 PR 必须人工批准。
- 不要在真实需求出现前做通用 DAG 或复杂工作流引擎。事件加规则加并行 lane 已经覆盖大多数个人场景。

### 5.6 如果只能先做三件事

1. 通道默认拒绝。
2. 交付链从 main 取 CI 和设置，并保护 CI、测试和交付设置路径。
3. 规则删除或改名时取消并通知孤立工作。

这三件直接决定它能不能从“个人可信环境里的工具”变成“敢让它自动干活的系统”。

## 6. 附录：与 OpenClaw / Hermes 的定位差异

这里的 Hermes 指本地 Agent 平台或网关，不是 Nous Research 的 Hermes 模型。两者在能力上有重叠，但不是同一层的东西。

| 维度 | OpenClaw、Hermes 这类产品 | agent-autoloop |
|---|---|---|
| 核心抽象 | 个人 Agent 操作系统或助理 | Agent 自动化中台或控制平面 |
| Agent 在哪里 | 通常内置 Agent 循环、记忆、人格、工具 | Agent 是外部 CLI 进程，中台不跑模型 |
| 主要入口 | 聊天、语音、画布、个人助理 | 事件、规则、卡片、审批、交付 |
| 状态 | 会话、记忆、用户画像 | 事实日志、投影、轮次、投递状态 |
| 强项 | 通用助理体验、工具生态、多模态、长期记忆 | 可审计、可重放、暂停不烧 token、多 Agent 调度、交付闭环 |
| 弱项 | 自动化治理和审计通常不是核心 | 没有记忆、人格、通用工具生态和聊天体验 |
| 安全模型 | 面向前台助理，攻击面更大 | 密钥种类、HMAC token、提示词边界更正式，但同用户 Agent 隔离弱 |
| 产品成熟度 | 功能广，面向普通用户 | 功能窄，面向技术用户 |

按功能广度看，它确实像简化版。按架构层次看，它不是子集。OpenClaw 这类产品是“Agent 自己干活”，agent-autoloop 是“中台决定谁在什么目录、用什么权限、干哪件事，然后记录和审批”。它把事件溯源、排队、审批、审计和交付做深了。

如果一定要类比，它更像“Temporal 或 Argo 加审批卡加事件日志，专门为 CLI Agent 服务”，而不是 OpenClaw 的轻量替代品。

组合方式也清楚：OpenClaw 或 Hermes 做前台入口和 Agent 运行时，agent-autoloop 做后台调度、审批和审计。但不要把 Agent 循环再做一遍，否则会变成两套互相打架的系统。
