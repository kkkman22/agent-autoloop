## 0. 执行摘要

第一阶段先做 8 个工作包，覆盖评审中的 15 个发现。顺序不是按文档编号，而是按风险和依赖排：

1. 先修通道默认拒绝和规则校验，阻止最直接的越权和静默丢活。
2. 再做规则生命周期，保证删除或改名规则不会留下永远不跑的队列和卡片。
3. 同时修 CI 范围脚本和交付信任链，保证自动合并不会被 PR 自己签发的 CI 绕过。
4. 最后做 HTTP、密钥、worker、CLI 和 MCP 的边界加固，再统一文档默认值。

关键路径是 `F0-02 规则校验` 到 `F0-03 规则生命周期`。`F0-01` 可以独立先做。`F0-04` 和 `F0-05` 需要仓库管理员配置分支保护，不能只靠代码 PR 完成。其余工作包可以并行。

## 3. 阶段 0 工作包

### F0-01 通道授权默认拒绝

**目标**

通道没有登记、没有回答者名单、回答者不在名单里，都不能改变卡片。只有显式通配才允许所有人。

**改动**

- `protocol/rules.ts`：校验 `rules.channels`；`answerers` 必须是字符串数组，元素不能为空；保留 `"*"` 作为显式通配；在加载规则时给出清楚的错误。
- `kernel/decide.ts`：`answer` 对通道回答先取 `rules.channels[channel]`；通道不存在就拒绝；`answerers` 缺失或为空就拒绝；`"*"` 才跳过名单检查；`by` 必须是非空字符串。
- `kernel/http.ts`：`/v1/cards/next` 只接受登记过的通道，未登记通道返回 401 或 404，不再进入长轮询。
- `cli/main.ts`：`init` 生成的 starter rules 里，交互通道补上 `answerers`；纯通知通道可以没有名单，但回答会被拒绝。
- 示例和测试夹具同步更新：`tests/rules.fixture.json`、`examples/`、`skills/agent-autoloop/SKILL.md` 里的规则示例。

**测试先行**

在 `tests/cards.test.ts`、`tests/http.test.ts`、`tests/channels.test.ts`、`tests/rules.test.ts` 增加：

- 通道没有 `answerers` 时回答被拒绝，卡片仍为 open。
- 通道未在 `rules.channels` 登记时拿不到卡片，也回答不了。
- `answerers: ["*"]` 时任意非空 `by` 可以回答。
- 回答者不在名单时仍然拒绝，原有测试保持。
- 通道答案的 `by` 为空或非字符串时拒绝。
- owner 通过 CLI 回答不受影响。

**文档**

更新 `docs/protocol.md` 的通道与回答章节，明确缺失名单是拒绝而不是放行；更新 `README.md` 和 `SECURITY.md` 的权限说明。这是一次有意的配置行为变化，发布说明要写清楚旧配置需要补 `answerers`。

**验收**

新增测试先失败再通过；`npm test` 全绿；没有未登记通道能收到卡片；owner 回答路径不变。

**风险**

纯通知通道没有 `answerers` 是允许的，但回答会被拒绝。文档必须区分“能收通知”和“能回答”。

### F0-02 规则校验加固

**目标**

规则里的来源、接单程序、代理、通道、目标都必须是真的自有键，不能命中 JavaScript 原型链；ID 和资源上限有明确边界。

**改动**

- `protocol/rules.ts`：`isKeyOf` 改用 `Object.hasOwn`；统一 ID 校验为小写字母、数字和短横线；拒绝 `__proto__`、`constructor`、`prototype`、`toString`、`hasOwnProperty` 等保留名；对 `parallel`、`timeout` 加上合理上限并给出错误。
- `protocol/rules.ts`：`emits.source`、`rule.to`、`rule.worker`、通道名、来源名都走同一套校验。
- 如果保留 `"*"` 通配回答者，只允许出现在 `answerers`，不允许出现在来源、代理、通道 ID 中。
- 规则加载失败仍走现有 `rulesError` 卡片，不新增数据迁移。

**测试先行**

在 `tests/rules.test.ts` 和 `tests/kernel.test.ts` 增加：

- `to: "constructor"`、`to: "toString"`、`to: "__proto__"` 被拒绝。
- 来源和通道使用原型链名字被拒绝。
- 大写、空格、斜杠、超长 ID 被拒绝。
- 合法的短横线 ID 仍然通过。
- `parallel: 0`、负数、超大数、`timeout: 0` 被拒绝或按约定处理。
- 规则加载失败不会留下可领取的 run。

**文档**

更新 `docs/protocol.md` 的规则字段表，写明 ID 字符集和上限；更新 `docs/plugins.md` 的插件命名约定。

**验收**

所有原型链名字都无法通过校验；旧合法规则不需要改；错误信息能指出具体字段。

### F0-03 规则生命周期清理

**目标**

删除或改名规则时，不再留下永远 queued 的轮次、永远 open 的卡片和“回答成功但没人处理”的状态。

**改动**

- `kernel/decide.ts` 的 `rules` 处理器：写入新规则后，扫描 queued run 和 open card。
- 对规则已不存在的 queued run：设置为 `cancelled`，写 `finished_at` 和说明，生成一张 notice 卡片，key 用 `run:<id>:rule-gone`，避免重复通知。
- 对规则已不存在的 open card：关闭卡片，结果写“对应规则已删除”，并生成一张 notice，key 用 `card:<id>:rule-gone`。
- 对规则已不存在的 decided card：如果它的 answer event 没有对应可领取 run，也关闭并通知，避免留下“已回答但不会执行”的卡片。
- `kernel/decide.ts` 的 `answer`：卡片对应规则不存在时返回 409 或 `InputError`，不记录 `card.answered` 事件；提示用户先用 `resolve` 关掉卡片。
- 重复应用同一份 rules 事实时不能重复生成通知；用现有卡片 key 的幂等性保证。

**测试先行**

在 `tests/rules.test.ts`、`tests/runs.test.ts`、`tests/cards.test.ts` 增加：

- 删除规则后，queued run 变为 cancelled，`claimNext` 不再返回它。
- 删除规则后，open card 被关闭，notice 只出现一次。
- 改名规则等价于删除旧规则加新增新规则。
- 删除规则后回答旧卡片返回 409，卡片保持 open，事件数不增加。
- 规则恢复后，新事件仍能正常入队。
- 规则重复加载不产生重复通知。

**文档**

更新 `docs/protocol.md` 的规则版本和轮次生命周期；更新 `README.md` 的规则编辑说明；在 `skills/agent-autoloop/SKILL.md` 里提醒删除规则会取消未完成工作。

**验收**

探针场景变成：删除规则后 `claimNext` 返回 null，但存在 cancelled run 和 notice；回答旧卡片被明确拒绝。所有新测试先失败再通过。

**风险**

“取消”是不可逆的产品选择。评审建议默认取消并通知；如果以后需要“暂停规则但保留队列”，在 F2-01 增加显式 `disable`，不要把删除当成暂停。

### F0-04 CI 范围脚本与保护路径

**目标**

PR 不能通过修改 `scripts/ci-scope.sh` 或测试文件让必需检查空转。

**改动**

- `.github/workflows/check.yml`：PR 场景从 base 提交读取范围脚本，而不是执行 PR 工作树里的脚本。用 `github.event.pull_request.base.sha` 取 `scripts/ci-scope.sh` 到临时目录后执行。
- `scripts/ci-scope.sh`：`.github/workflows/**`、`scripts/**`、`tests/**`、`package.json`、`package-lock.json`、`ops/delivery.json` 一律 `scope=full`。`.github/ISSUE_TEMPLATE` 和文档模板仍可 docs。
- `CONTRIBUTING.md`、`AGENTS.md`：写明受保护路径和人工批准规则。
- 新增 `tests/ci-scope.test.ts`：在临时 git 仓库里构造 docs、normal、full、受保护路径和 PR 场景，调用脚本检查输出。
- 仓库外配置：要求 `main` 开启分支保护，要求 `check` 两个矩阵任务通过，要求受保护路径的 PR 由 CODEOWNERS 或管理员批准，禁止 force push 和删除分支。

**测试先行**

测试覆盖：

- 只改 README 输出 docs。
- 改 `kernel/` 或 `protocol/` 输出 full。
- 改 `scripts/ci-scope.sh`、`tests/`、`.github/workflows/`、`ops/delivery.json` 输出 full。
- PR 场景使用 base 脚本，不执行 PR 修改后的脚本。
- 无法取得 diff 时输出 full。

**文档**

更新 `CONTRIBUTING.md`、`AGENTS.md`、`.github/pull_request_template.md`，写清楚哪些改动必须人工批准。

**验收**

即使 PR 把 `scripts/ci-scope.sh` 改成输出 docs，工作流仍按 base 脚本得到 full；测试文件被修改时也跑 full。分支保护配置完成并截图或记录在发布检查清单里。

**风险**

代码只能降低风险，不能替代仓库管理员设置。分支保护和 CODEOWNERS 是 P0 的外部前置条件。

### F0-05 交付信任链

**目标**

自动合并只信任来自 main 的 CI 定义和交付设置；PR 修改 CI、测试或交付配置时，默认转人工。

**改动**

- `ops/delivery.json` 增加受保护路径配置，默认包含 `.github/**`、`scripts/**`、`tests/**`、`package.json`、`package-lock.json`、`ops/delivery.json`。
- `plugins/delivery/project.ts`：解析和校验受保护路径；设置只从受保护的 main 读取。
- `plugins/delivery/delivery.ts`：在 fetch 后比较 `main...head` 的变更文件；命中受保护路径且没有 `deliver-attended` 标签时返回“需人工”或 `reviewOnly`，不自动合并。
- `plugins/delivery/delivery.ts` 的 `fullCheck`：确认 check workflow 文件在 head 与 main 一致；不一致时不自动合并。
- `plugins/delivery/action.ts`：Ship 判定读取合并前 main 的设置，不使用 target 的设置；如果无法确定合并前 main，默认要求人工发布。
- `plugins/delivery/action.yml`：补充说明和输入参数。
- 不改变现有四个标签的语义，只让 `deliver-attended` 成为受保护路径的人工确认。

**测试先行**

在 `tests/delivery.test.ts`、`tests/delivery-action.test.ts`、`tests/delivery-scope.test.ts` 增加：

- PR 只改业务代码，正常自动交付。
- PR 改 `.github/workflows/check.yml`，不自动合并。
- PR 改 `tests/` 或 `package.json`，不自动合并。
- 有 `deliver-attended` 时允许继续，但仍记录原因。
- check workflow 文件在 head 与 main 不一致时不自动合并。
- Ship 设置来自合并前 main，target 修改设置不影响本次判定。
- 设置文件缺失或格式错误时安全失败。

**文档**

更新 `docs/plugins.md`、`ops/delivery.json` 示例、`README.md` 交付章节和 `SECURITY.md`。写清楚“LLM 审查不是安全门禁”。

**验收**

受保护路径 PR 无法自动合并；Ship 不再读取 target 设置；所有交付测试使用假 IO，不访问真实 GitHub。

**风险**

如果现有项目依赖 `deliver-attended` 之外的自动路径，需要一次迁移说明。默认安全失败会降低自动化速度，这是有意取舍。

### F0-06 HTTP、密钥与 worker 加固

**目标**

把低成本的网络安全、文件权限和结果保留问题一起修掉，减少远程部署和主密钥轮换时的损失。

**改动**

- `kernel/http.ts`：`cardAtLink` 的 GET 也检查 7 天过期，过期返回 410 或只显示已过期；`readText` 超过 1MB 的请求体不再留用，但最多再读 8MB 丢弃后才返回 413：一到 1MB 就断会让响应先于对方的发送到达，连接被重置，对方连接池里的下一个请求会无故失败。
- `host/runtime.ts`：启动时检查并修正 `master.key`、`config.json`、`hub.db` 的权限；拒绝符号链接形式的密钥文件。
- `host/up.ts`：加载 `secrets.env` 前检查权限并修正到 0600；必要时设置进程 umask。
- `cli/main.ts`：`join` 对非 loopback 的 `http://` 直接拒绝，提示使用 https 或 SSH 隧道；loopback 仍允许 http。
- `worker/worker.ts`：`settle` 遇到 401/403 时保留 `entry.json` 和结果，不删除；记录告警并按退避重试。其他 4xx 仍按现有规则处理。
- 新增 `tests/permissions.test.ts`：临时 HOME 下检查 `master.key`、`secrets.env`、`config.json`、`hub.db` 的权限修正和符号链接拒绝。
- 新增 `tests/rate-limit.test.ts`：请求体超限、长轮询上限和每密钥并发限制。
- `tests/cards.test.ts`、`tests/http.test.ts`、`tests/join.test.ts`、`tests/worker*.test.ts` 补对应行为。

**测试先行**

- 过期卡片 GET 返回 410，POST 仍拒绝。
- 2MB 请求体返回 413，且不会先完整读入 8MB。
- 已存在的 0644 `master.key` 启动后被修正为 0600。
- 指向别处的 `master.key` 符号链接被拒绝。
- 非 loopback 的 `http://` join 被拒绝，`https://` 和 loopback 通过。
- worker 收到 401 后 entry 仍存在，后续成功时能提交结果。

**文档**

更新 `INSTALL.md`、`SECURITY.md`、`docs/protocol.md` 的连接和权限章节。写清楚同用户 Agent 的剩余风险，以及独立用户或容器的建议。

**验收**

权限测试在 macOS 和 Linux 都通过；worker 401 测试不依赖真实网络；`host/http.ts` 仍不超过 50 行。

### F0-07 CLI、MCP 与输出边界

**目标**

Agent 不能默认通过 MCP 获得本人写权限；CLI 不把不可信文本直接送进终端；超长 tell 和超前 delivered 版本有明确处理。

**改动**

- `cli/mcp.ts`：默认只暴露 `status`、`why` 等只读工具；`answer`、`resolve`、`stop`、`emit`、`tell` 需要显式 `--allow-writes` 或环境变量开关；工具注解标明读写属性。
- `cli/main.ts`、`cli/why.ts`：新增可打印文本处理，默认剥离 ANSI/OSC 控制字符；增加 `--raw` 保留原样。
- `kernel/http.ts`：`tell` 的文本上限按通道能力校验。P0 先统一为 2000 字并返回 400，或在规则里增加 `maxText` 后按最小值拒绝；长文本分片放到 P2。
- `kernel/decide.ts`：`delivered` 拒绝大于当前卡片版本的报告，返回 400 或忽略并记录。
- `tests/mcp.test.ts`、`tests/status-cost.test.ts`、`tests/why.test.ts`、`tests/cards.test.ts`、`tests/http.test.ts` 补测试。

**测试先行**

- MCP 默认工具列表没有写操作；加 `--allow-writes` 后出现。
- 卡片标题包含 ANSI 序列时 `status` 输出无可执行控制字符；`--raw` 保留。
- 超过通道上限的 `tell` 返回 400，不会创建会永远失败的卡片。
- `delivered` 上报未来版本被拒绝，正常版本仍更新。

**文档**

更新 `skills/agent-autoloop/SKILL.md`、`README.md`、`docs/protocol.md` 的 MCP、CLI 和 tell 章节。

**验收**

Agent 默认无法通过 MCP 改变状态；终端输出不可注入控制序列；超长文本在入口被拒绝而不是在通道里无限重试。

### F0-08 文档与默认值统一

**目标**

让文档、示例和代码对同一件事说同一种话，避免用户照抄失败。

**改动**

- `protocol/rules.ts` 的 `ASK_FIRST` 与 README、`docs/protocol.md`、`skills/agent-autoloop/SKILL.md` 统一。建议保留代码里的 7 项，因为它是更安全的方向，把文档改成 7 项。
- 协议示例里的 JSONC 注释改成纯 JSON；如果产品决定支持 JSONC，放到 F2-01，不在 P0 临时加解析器。
- `examples/`、`tests/rules.fixture.json`、`skills/agent-autoloop/SKILL.md` 同步新的 `answerers`、规则 ID 和默认值。
- `CHANGELOG.md` 或发布说明记录配置行为变化：通道需要 `answerers`、远程 join 需要 https、MCP 写工具需要显式开关、tell 上限变化。

**测试先行**

- `tests/rules.test.ts` 断言默认 `askFirst` 与文档约定一致。
- `tests/business-recipes.test.ts` 和 `tests/examples.test.ts` 使用新示例通过。
- 文档示例可以被 `JSON.parse` 直接解析。

**验收**

所有示例可直接运行；文档和代码默认值一致；发布说明列清楚不兼容配置。

## 4. 阶段 1 工作包

### F1-01 备份、恢复与主密钥轮换

- 增加 `agent-autoloop backup <path>` 和 `restore <path>`。
- 使用 `node:sqlite` 提供的备份能力或 `VACUUM INTO`，先做 spike 验证 WAL 下的一致性；备份必须包含 `hub.db`、`master.key`、`config.json`、`secrets.env` 和清单文件。
- 恢复时要求 hub 已停止，校验清单和格式指纹，恢复后修正权限。
- 主密钥轮换要有明确流程：停止接单、等待或取消在跑轮次、备份、轮换、重建投影、重启；文档说明卡片链接和 run token 会失效。
- 测试使用临时 HOME 和临时数据库，不碰真实数据。
- 验收：备份、修改、恢复后状态一致；权限正确；恢复失败不会破坏原数据。

### F1-02 指标与状态聚合

- 增加 owner-only 的结构化指标端点，输出事实总数、数据库大小、各状态轮次数、投递失败、通道放弃、worker 在线数、每规则成本和投影重建进度。
- 优先用普通文本或 Prometheus 文本格式，不引入依赖。
- 对 `state` 的 per-rule 统计做按日聚合投影，避免每次扫描全部历史；先测量，再决定是否需要新投影。
- 测试覆盖指标权限、空库、运行中、失败和恢复场景。
- 验收：百万级事实下 `state` 和指标查询达到可接受延迟；指标不泄露密钥和卡片正文。

### F1-03 限流、隔离与退避

- 在 host 层增加每密钥并发、请求速率和长轮询上限；不把限流状态写进事实日志。
- `host/up.ts` 的通道重启加指数退避，避免插件立即返回时热循环。
- `worker/worker.ts` 的 tick 做异常隔离，单个坏 entry 不拖垮整个循环。
- 测试覆盖超限、通道崩溃、worker 异常和恢复。
- 验收：远程部署不会因为一个密钥或一个通道耗尽进程；日志能说明限流原因。

### F1-04 日志增长与投影重建

- 先写设计文档，不改协议：事实日志是权威，checkpoint 或归档必须可验证、可恢复、可回滚。
- 给投影重建增加进度和可恢复状态；对 100 万级事实做基准。
- 评估 `projection_refs` 的增长和 `why` 查询成本，再决定是否需要保留策略。
- 只有在设计、测试和回滚方案都齐备后才实现归档；本阶段可以先只做聚合和重建优化。
- 验收：重建中断后可继续；归档方案有恢复演练；不破坏事实日志的权威性。

### F1-05 发布工程与 soak

- 增加语义化版本标签、`CHANGELOG.md`、`update --check` 和升级说明。
- `install.sh` 支持安装指定标签；`update` 支持回滚到上一个标签。
- CI 增加 24 小时 soak 和故障注入；nightly 保留 SIGKILL、变异和性能基准。
- 发布检查清单包含分支保护、受保护路径、备份和恢复演练。
- 验收：升级、回滚、恢复各演练一次；发布说明能追溯到具体提交。

## 5. 阶段 2 工作包

### F2-01 规则编辑体验

- 增加 `rules validate`、`rules explain`、`rules diff`、`rules disable`、`rules edit`。
- 规则变更前展示会影响哪些 queued run 和 open card；`disable` 是显式暂停，不删除队列。
- 支持 JSONC 或提供纯 JSON 模板；如果支持 JSONC，使用无依赖的词法处理，不引入第三方库。
- 测试覆盖编辑、校验、解释、禁用、启用和删除；不改变协议既有字段。
- 验收：用户不需要手改 JSON 就能安全删除或暂停规则；删除不再静默丢活。

### F2-02 路由与审批角色

- 规则级 `channels`、安静时段、严重级别、回答者角色；默认值保持现有行为。
- `nextCard` 按规则和通道选择卡片；避免一张卡片发给所有通道。
- 回答者角色与通道 `answerers` 兼容，不破坏现有配置。
- 测试覆盖多通道、安静时段、角色拒绝和 fallback。
- 验收：一个 hub 可以服务多个受众；隐私边界清楚；旧配置不需要迁移。

### F2-03 参考客户端

- 独立仓库实现总览页，使用 `/v1/state` 和 `/v1/stream`。
- 展示待回答卡片、最近失败、每规则成本、投递状态和 worker 在线情况。
- 不在本仓库的 `kernel/` 或 `host/` 加页面；只补协议文档和示例客户端链接。
- 验收：参考客户端能在十分钟内展示第一张卡片；协议字段稳定；没有产品名进入内核。

### F2-04 插件生态与平台支持

- 增加插件清单、版本、兼容性声明和签名校验；`add` 和 `update` 能验证来源。
- 提供 worker 独立用户或容器运行的安装选项；Windows 通过 WSL 或容器给出明确路径。
- 测试覆盖插件安装、更新、版本不兼容和签名失败。
- 验收：插件升级可追溯；不引入运行时依赖；内核仍不导入插件。

### F2-05 交付扩展

- 把 GitHub 交付的 `DeliveryIO` 抽象扩展到 GitLab 或其他托管。
- 受保护路径策略和人工审批门作为通用能力，不绑定单一平台。
- LLM 审查保持建议角色，不作为自动合并的唯一门禁。
- 测试使用假 IO，不访问真实仓库；真实端到端脚本只在用户明确要求时运行。
- 验收：新托管平台通过同一套行为测试；现有 GitHub 交付不回退。

## 8. 发布与回滚

- P0 完成后建议发布一个 minor 版本，例如 `v1.1.0`，因为通道 `answerers` 和 MCP 默认值有配置行为变化。
- 发布说明必须列出：通道需要 `answerers`、未登记通道不能收卡、远程 `http://` join 被拒绝、MCP 写工具需要显式开关、`tell` 上限变化、卡片链接过期行为。
- 不做数据迁移。规则删除产生的 cancelled run 和 notice 是新事实，投影从日志重建即可。
- 回滚代码不丢数据。主密钥不变时，卡片链接和 run token 继续有效；如果执行了主密钥轮换，回滚不能恢复旧 token，需要按 F1-01 的流程处理。
- 发布前检查：`npm test`、`typecheck`、`format:check`、nightly 相关项、分支保护、受保护路径、备份演练。

## 9. 风险与待决策

| 风险或决策 | 建议 | 说明 |
|---|---|---|
| `answerers` 缺失怎么处理 | 默认拒绝，加载时警告 | 安全优先；纯通知通道可以没有名单 |
| 规则删除是取消还是保留 | 默认取消并通知 | 删除不等于暂停；暂停用 F2-01 的 disable |
| CI 能否完全靠代码防住 | 不能 | 必须配合分支保护和人工批准 |
| MCP 默认是否可写 | 默认只读 | 写工具用显式开关 |
| tell 超长怎么处理 | P0 先拒绝，P2 再做分片 | 避免通道无限重试 |
| 同用户 Agent 隔离 | 文档加独立用户或容器建议 | 代码无法彻底解决 |
| askFirst 默认 7 还是 4 | 文档改成 7 | 保留更安全的行为 |
| 卡片链接过期返回什么 | GET 和 POST 都 410 | 语义比 401 更准确 |
| 日志归档何时做 | 先设计，后实现 | 不能破坏事实日志权威 |
