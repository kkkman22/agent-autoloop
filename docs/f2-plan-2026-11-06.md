## 3. F2-01 规则编辑体验

### 目标

用户不手改 JSON 也能检查、理解、预览、暂停和删除规则；删除前看得到会取消哪些活、关掉哪些卡片；想停一阵子用暂停，暂停不丢活。

### 现状

- `agent-autoloop check` 只读 `rules.json` 并报错，不说哪一条事件会交给谁。
- 删掉或改名一条规则，`kernel/decide.ts` 的 `dropRules` 会取消还没领走的轮次、关闭对应卡片并发通知。没有“先停一下”的办法。
- `protocol/rules.ts` 的 `checkFields` 拒绝不认识的字段，所以加字段是不兼容旧版本中台的改动，回滚时要注意（见“兼容”）。

### 协议改动

1. 规则加可选字段 `disabled`（布尔，默认 `false`）。
   - 事件规则暂停时：事件照常记录，`routed` 照常包含这条规则，照常排进队列（D2）；`claimNext` 不派这条规则的轮次。回答这条规则的卡片也照常排队，等恢复。
   - 定时规则暂停时：`tick` 跳过它，不补（D3）。恢复时从下一次到点开始。
   - `/v1/state` 的 `lines` 每项加 `disabled`；`totals` 里排队数照常算。
2. 新增只读请求 `POST /v1/rules/preview`，只认本人密钥。请求体是一份候选规则（JSON 文本），中台用 `protocol/rules.ts` 校验，再在当前视图上空跑一次 `decide(view, {type: "rules"})`，**不提交**，把这次会产生的变化归纳成：
   - 新增、删除、改名、改动的规则；
   - 会被取消的排队轮次（按规则计数，带前 20 个编号）；
   - 会被关闭的卡片（按规则计数，带前 20 个编号和标题）；
   - 已领取的轮次照旧跑完，单独列出。
   空跑只用内核现有的纯函数，不写事实；测试要证明请求前后日志条数不变。
3. 校验错误的说明保持现在的中文格式；`validate` 额外给出“警告”（不阻止生效），比如通道没有 `answerers` 只能发通知、规则引用的来源还没有密钥、规则的 `cwd` 在这台电脑上不存在。

### 命令

| 命令 | 做什么 | 需要中台在跑 |
| --- | --- | --- |
| `rules validate [文件]` | 校验并给出警告；不写文件 | 否 |
| `rules explain <来源> <事件类型>` | 列出会接这条事件的规则、交给哪个 Agent、哪台接单程序、什么目录和权限、同组并发和事项拆分 | 否 |
| `rules explain <规则名>` | 一条规则的完整说明；定时规则列出接下来 3 次到点时间（按规则时区） | 否 |
| `rules diff [文件]` | 候选文件和正在用的规则逐条对比，再调用预览列出影响 | 是 |
| `rules disable <规则名>` / `rules enable <规则名>` | 改 `disabled`，先预览，确认后写回 | 是（预览） |
| `rules remove <规则名>` | 删掉一条规则，先预览要取消和关闭的东西，确认后写回 | 是（预览） |
| `rules edit` | 用 `$EDITOR` 打开一份临时副本；保存后校验、对比、预览，确认后替换 | 是（预览） |

写回 `rules.json` 的步骤固定为：校验候选 → 预览 → 终端确认（非交互要 `--yes`，没有就拒绝）→ 把旧文件复制成 `rules.json.<时间>.bak` → 写临时文件 → 原子改名。中台照常靠文件监视在几秒内生效。`check` 保留为 `rules validate` 的别名。

### 改动的文件

- `protocol/rules.ts`：认 `disabled`；`validate` 的警告放在一个新函数里，不进 `parseRules`。
- `kernel/rules.ts`：`Rule` 类型加 `disabled`。
- `kernel/decide.ts`：`claimNext` 的可领条件跳过暂停的规则；`tick` 跳过暂停的定时规则；`dropRules` 不变。
- `kernel/query.ts`：新增 `previewRules(view, rules, now, env)`，返回上面的归纳结果；只读。
- `kernel/http.ts`：加 `POST /v1/rules/preview`。
- `kernel/state.ts`：`lines` 加 `disabled`。
- `cli/rules.ts`（新）：上面的命令；`cli/main.ts` 只接线。
- `protocol/schema.json`：加 `rules-preview` 请求和响应。

### 先写的失败测试

- `tests/rules-cli.test.ts`（新）：validate 的错误和警告；explain 对通配类型、并发规则、定时规则的输出；disable 之后文件里只多了这一个字段并留下备份；非交互没有 `--yes` 时不写文件；编辑后写错的规则不替换原文件。
- `tests/rules-preview.test.ts`（新）：删一条有排队轮次和开着卡片的规则，预览列出的和真正生效后发生的完全一致；预览前后事实条数不变；非本人密钥 401；请求体超过上限 413。
- `tests/rule-lifecycle.test.ts` 加用例：暂停的事件规则来了三条同一事项的事件，只排成一轮且不派；恢复后派一次、带着三条事件；暂停的定时规则跨过两次到点，恢复后不补；暂停期间回答卡片，恢复后回答叫醒原事项。
- `sim/`：随机输入加“暂停/恢复一条规则”；不变量加“暂停中的规则不会有新领取的轮次”。变异清单加一条：去掉 `claimNext` 里对 `disabled` 的判断，测试必须抓到。

### 验收

- 用户能用命令暂停、恢复、删除规则，删除前看到的影响和实际发生的一致。
- 暂停期间来的事件，恢复后一条不少地处理。
- `npm test`、`typecheck`、`format:check`、`test:nightly` 的模拟与变异部分通过。

### PR 拆分

1. PR 1：`rules validate`、`rules explain`（纯本地，不改内核）。
2. PR 2：`disabled` 字段及内核行为、模拟和变异（改内核，完整检查）。
3. PR 3：`POST /v1/rules/preview` 和 `diff`、`disable`、`enable`、`remove`、`edit`。

### 兼容

- 旧的 `rules.json` 不用改，行为不变。
- 用过 `disabled` 之后回滚到旧版本：旧版本不认这个字段，启动时会拒绝规则文件。回滚前先 `rules enable` 或删掉这个字段。这一条写进 CHANGELOG 的“要注意”。

## 4. F2-02 路由与审批角色

### 目标

一个中台能服务好几拨人：私人反馈只发本人，告警发运维群；夜里不打扰，紧急的照发；谁能回答由角色决定，不再只看通道的名单。旧配置一个字不用改。

### 现状

- `kernel/decide.ts` 的 `nextCard` 对任何已登记的通道都会交出所有候选卡片：每张卡片发给所有通道。
- 回答的核对只看通道的 `answerers` 和送达记录（`answer` 里的回答者检查和原消息检查）。
- 卡片行上已经有 `rule`、`lane`、`grp`；系统卡片（`tell`、规则写错、接单程序离线、事件循环）没有 `rule`。

### 协议改动

1. 规则加可选字段：
   - `channels`：通道编号的列表，这条规则产生的卡片只发给这些通道。不写就是所有通道（现在的行为）。
   - `severity`：`low`、`normal`（默认）、`urgent`。`urgent` 不受安静时段限制；`low` 照常发送，但卡片视图带上 `severity`，桌面通道据此不弹出、只记下（其他通道插件自行决定）。
   - `answerers`：角色或人的列表，例如 `["role:运维", "ou_xxx"]`。写了以后，回答者既要在通道的 `answerers` 里，也要在这里；本人用命令行或本人密钥回答不受限制。
2. 通道加可选字段 `quiet`：`{ "from": "22:00", "to": "08:00" }`，按 `rules.json` 的时区。安静时段里，这个通道领不到非 `urgent` 的卡片；时段结束后照常补发。`from` 和 `to` 不能相同。
3. 顶层加可选字段：
   - `roles`：`{ "运维": ["ou_a", "13800000000"] }`，每个角色是各通道里那个人的写法列表（D6）。
   - `notices`：`{ "channels": ["chat"] }`，没有规则的系统卡片发到哪（D5）。不写就是所有通道。
4. 卡片创建时把算好的目标通道写在卡片上（新列 `channels`，JSON 列表；`null` 表示所有通道），把允许的回答者写成 `answerers`（同样 `null` 表示不额外限制）。见 D4。
5. 卡片视图（通道拿到的 JSON）加 `severity`。旧通道插件忽略它即可。

### 改动的文件

- `protocol/rules.ts`、`kernel/rules.ts`：认新字段；`roles` 引用不存在的角色、`channels` 引用没登记的通道、`quiet` 的时间写错都报错。
- `kernel/decide.ts`：
  - `createCard` 和 `cardFromReceipt` 按规则（或 `notices`）算出 `channels`、`answerers`、`severity` 写进卡片。
  - `nextCard`：卡片的 `channels` 不含这个通道就跳过；通道在安静时段里且卡片不是 `urgent` 就跳过。时间判断用传进来的 `now` 和规则时区，内核不读时钟。
  - 桌面通道（`plugins/desktop/channel.ts`）读 `severity`：`low` 不弹出。
  - `answer`：通道转达的回答，在现有两道核对之外，再核对卡片的 `answerers`（展开角色后）。
- `kernel/evolve.ts`：`projection_pending` 的逻辑不变；`deliveryCandidates` 仍按现在的 SQL 取候选，过滤在 `nextCard` 里做。开着的卡片数量通常很少，不需要新索引；夜间基准要确认这一点。
- 安静时段结束不会主动叫醒正在长轮询的通道：通道最多 50 秒就会重新来领，所以最晚晚 50 秒补发。这是接受的代价，写进协议，不为它加到期表项。

### 先写的失败测试

- `tests/routing.test.ts`（新）：规则指定一个通道，另一个通道领不到它的卡片；不写 `channels` 时两个通道都能领到（旧行为）；系统卡片按 `notices.channels` 发；卡片创建后改规则，已有卡片的去向不变，新卡片按新规则走；`why` 能查到卡片当时的去向。
- 安静时段：时段内普通卡片不交出、紧急卡片交出；时段跨午夜；时段结束后补发；规则时区不是本机时区时按规则时区算；安静时段不让送达重试的计时提前耗尽（放弃计时从第一次真正交出算起）。
- 角色：角色里的人能回答、不在角色里的人被拒（401，原因写清）；本人密钥回答不受限制；通道 `answerers` 是 `["*"]` 但规则有角色时，以角色为准；角色引用了不存在的角色名，`rules.json` 校验报错。
- `tests/cards.test.ts`、`tests/channels.test.ts` 的现有用例一个不改，全部照过：这是“旧配置不用改”的证明。
- `sim/`：随机配置里加多通道和角色；不变量加“卡片只送达给它的目标通道”“回答者在卡片允许的名单里”。变异清单加两条：去掉 `nextCard` 的通道过滤、去掉 `answer` 的角色核对。

### 验收

- 两拨人共用一个中台时，一方的卡片不会出现在另一方的通道里。
- 夜间不打扰，紧急的照发，早上补发。
- 旧的 `rules.json` 原样通过全部现有测试。

### PR 拆分

1. PR 1：规则 `channels` 和顶层 `notices`，卡片记录去向。
2. PR 2：`severity` 和通道 `quiet`。
3. PR 3：`roles` 和规则 `answerers`。

每个都改内核，都跑完整检查和夜间的模拟、强杀、变异。卡片行加列会改格式指纹，升级后第一次启动重建一次视图。

### 兼容

- 新字段全部可选，不写就是现在的行为。
- 和 F2-01 一样：用了新字段再回滚，旧版本会拒绝规则文件，回滚前先删掉新字段。
- 第三方通道插件不用改；想按紧急程度区别对待的，读卡片里的 `severity`。

### 隐私边界（写进 SECURITY）

- 规则级 `channels` 是“只发给谁”，不是加密：本人密钥仍然看得到全部卡片。
- 系统卡片默认仍发所有通道。处理私人资料的中台，要用 `notices.channels` 把它们收回到本人通道。

## 5. F2-03 参考客户端

### 目标

给想要总览页的人一个能直接跑的例子，证明不用改中台、只靠 `/v1/state` 和 `/v1/stream` 就能做出来；同时把这两个接口的字段定成稳定的约定。

### 在本仓库做的（PR 1）

- `protocol/schema.json` 加 `state` 响应的 JSON Schema，覆盖 `docs/protocol.md`「本人」一节列出的全部字段。
- `tests/state-schema.test.ts`（新）：用固定种子跑一段业务，`/v1/state` 的每次响应都要通过这份 Schema；字段改名或删掉会让它失败。
- `docs/protocol.md` 加一节“写一个客户端”：本人密钥只放在服务端；`/v1/stream` 断线续读；哪些字段保证稳定、新增字段客户端要忽略。
- README 的“更多文档”加参考客户端的链接。

### 在新仓库做的（D10）

- 一个 Node 24 小服务，无依赖：读本人密钥和中台地址，给浏览器发一张静态页，代理 `/v1/state`，用 SSE 转发 `/v1/stream`。密钥不发到浏览器，所以中台不需要 CORS。
- 页面显示：待回答的卡片（只读，回答用命令或通道）、最近失败的轮次、每条规则的轮数和费用、各通道的送达和放弃、接单程序在不在线。
- 测试：起一个本仓库的临时中台（随机端口、临时 `AGENT_AUTOLOOP_HOME`），跑一遍提问，页面数据里出现这张卡片。

### 验收

- 从克隆到看到第一张卡片不超过十分钟（按新仓库 README 的步骤计时）。
- 本仓库的 `kernel/`、`host/` 没有任何改动；没有产品名进入内核。

## 6. F2-04 插件生态与平台支持

### 目标

装插件、升级插件都能追溯到具体版本和签名人；不兼容的插件装不上；给要隔离 Agent 的人一条明确的装法。

### 现状

- `agent-autoloop add <git 地址>` 只是 `git clone` 到 `~/.agent-autoloop/plugins/<仓库名>`，不记版本、不能更新、不验证来源。
- `host/plugins.ts` 按名字加载，安装目录优先于内置。

### 设计

1. 插件仓库根目录可以放 `plugin.json`：
   ```json
   { "name": "qq", "version": "1.2.0", "provides": ["channel"], "engine": ">=1.1.0 <2.0.0", "description": "QQ 群机器人通道" }
   ```
   `engine` 只支持 `>=a.b.c`、`<a.b.c` 和两者组合，解析写在 `host/semver.ts`（几十行）。
2. 安装记录 `~/.agent-autoloop/plugins.lock.json`，权限 0600：名字、地址、提交、版本、签名人（没签名就是 `null`）、安装时间。
3. 签名（D7、D8）：插件发布者用 SSH 密钥给版本标签签名。用户用 `agent-autoloop plugins trust <名字> <公钥文件>` 登记，写进 `~/.agent-autoloop/allowed_signers`。之后 `add` 和 `update` 用 `git -c gpg.format=ssh -c gpg.ssh.allowedSignersFile=… verify-tag` 验证。
4. 命令：
   | 命令 | 做什么 |
   | --- | --- |
   | `add <地址> [--ref 版本]` | 克隆、读清单、核对兼容和签名、写安装记录；不兼容或签名不对就删掉克隆、报错 |
   | `plugins list` | 名字、版本、提交、签名人、是否兼容 |
   | `plugins update <名字> [--check]` | 拉新标签，核对兼容和签名后再切换；失败停在原版本 |
   | `plugins trust <名字> <公钥文件>` | 登记信任的公钥 |
   | `plugins remove <名字>` | 删掉目录和记录 |
5. `doctor` 报告：没有清单的、没签名的、和当前版本不兼容的插件。`loadPlugin` 不改：加载时不做网络或签名操作，免得通道每次重启都去验签。
6. 隔离和平台（只写文档和示例，不进 CI）：
   - `examples/isolation/`：用单独系统账号跑接单程序的 systemd 单元和 launchd 配置示例，说明要本人自己用 sudo 建账号；容器示例 `Dockerfile`（基于官方 Node 24 镜像，只跑 `join` 出来的接单程序）。
   - INSTALL 加 Windows 一节：用 WSL2 装 Linux 版；不支持原生 Windows。

### 先写的失败测试

- `tests/plugins-cli.test.ts`（新），用本地临时 Git 仓库当插件源，不联网：带清单装上并写记录；`engine` 不兼容拒装且不留目录；登记了公钥后，没签名或签名人不对的标签拒装、拒更新，原版本照常可用；`update --check` 不改任何东西；名字以 `-` 开头或含 `/` 的拒绝；清单里的 `name` 和仓库名不一致时报错。
- `tests/plugins.test.ts` 现有用例照过：没有清单的老插件照常加载。
- 签名测试需要 `ssh-keygen` 和 Git ≥ 2.34；CI 的 ubuntu 和 macOS 镜像都有。没有时跳过并写明原因。

### 验收

- 每个装着的插件都查得到版本、提交和签名人。
- 不引入运行时依赖；内核仍不导入插件。

### PR 拆分

1. PR 1：清单、兼容检查、安装记录、`plugins list|remove`。
2. PR 2：签名、`plugins trust`、`plugins update`。
3. PR 3：隔离示例和 Windows 文档。

## 7. F2-05 交付扩展

### 目标

交付流水线不绑在 GitHub 上：受保护路径、人工确认、检查定义一致、合并后核实发布这些规则对任何托管平台都一样，换平台只换一层薄的接口。

### 现状

- `plugins/delivery/delivery.ts` 的 `DeliveryIO` 里，`api(path)` 直接用 GitHub REST 的路径（`statuses/…`、`pulls/…`、`actions/workflows/…`），业务逻辑和 GitHub 的接口形状缠在一起。
- 现有交付测试的假 IO 也是按 GitHub REST 路径写的。

### 设计

1. 在 `plugins/delivery/host.ts`（新）定义平台无关的接口 `DeliveryHost`：取变更（PR/MR）及其头提交、标签、作者；设置提交状态；读检查结果（通过、等待、失败）和检查定义文件；合并（带“头提交必须是这个”的条件）；关闭自动合并并读回确认；比较两个提交；列变更文件；读主分支最新提交。
2. `plugins/delivery/github.ts` 改成实现 `DeliveryHost`，内部仍用现有的 `gh api` 调用。`delivery.ts` 的业务逻辑只用 `DeliveryHost`。
3. **现有测试一个不改**：它们的假 IO 按 GitHub REST 路径回答，正好经过新的 GitHub 实现，等于同时证明了这层翻译没走样。
4. 新增 `plugins/delivery/gitlab.ts`（D9）：用 `glab api` 调 GitLab REST（合并请求、流水线、提交状态、标签），合并用 `sha` 条件防止提交变化后误合。
5. 新增按平台参数化的行为测试 `tests/delivery-hosts.test.ts`：同一组场景（受保护路径不自动合并、检查定义和 main 不一致不合并、草稿不放行、提交或 main 变化不合并、合并响应丢了读回、Ship 用合并前 main 的设置）分别对“假 GitHub REST”和“假 GitLab REST”跑一遍。
6. Ship：GitHub 继续用本仓库的 Action；GitLab 提供 `plugins/delivery/gitlab-ci.yml` 模板，调用同一个 `run.ts` 的发布判断。依赖的外部镜像固定到摘要。
7. 设置文件 `ops/delivery.json` 加可选 `host`（`github` 默认、`gitlab`），GitLab 的项目写成 `group/project`。

### 先写的失败测试

- `tests/delivery-hosts.test.ts`（新）：上面的场景，先只对假 GitHub 跑，证明抽象之后行为不变；再加假 GitLab。
- GitLab 特有：合并请求的“草稿”和“需要批准”状态不被当成可合并；流水线状态的各种取值（`manual`、`skipped`）不被当成通过。
- 现有 `tests/delivery*.test.ts` 全部照过。

### 真机验证

`scripts/delivery-e2e.ts` 加 `--host gitlab`。和 GitHub 版一样，只在用户明确要求、给出 `group/project --run` 时才会建、删真实的测试项目。

### 验收

- 第二个平台通过同一套行为测试；现有 GitHub 交付一项不退。
- LLM 审查仍只是建议，不作为自动合并的唯一门禁。

### PR 拆分

1. PR 1：`DeliveryHost` 接口和 GitHub 实现，业务逻辑改用接口，现有测试照过。
2. PR 2：参数化行为测试（先只有 GitHub）。
3. PR 3：GitLab 实现、假 GitLab、CI 模板、文档。

`plugins/delivery/` 的 PR 在 CI 里是普通范围；PR 2、PR 3 改了 `tests/`，按规则要完整检查并人工批准。

## 8. 每个 PR 都要做的事

- 测试先写并确认它在改动前是失败的；测试文件开头写防的失败方式。
- 改了 `kernel/`、`protocol/` 或 `sim/`：`npm test`（含 20 万步模拟和穷举）、`typecheck`、`format:check`，再跑 `test:nightly` 的模拟、强杀和变异。本机的空闲内存预算原来就不过（114 MB 对 60.4 MB），以和基线一致为准。
- 没动这三处：`npm run test:quick`、`typecheck`、`format:check`。
- 新加目录或让测试读某份文档时，同步改 `scripts/ci-scope.sh` 和它的测试。
- 改协议的 PR：同步 `docs/protocol.md`、`protocol/schema.json`、两份 README 的“这次改了什么”、`CHANGELOG.md`、SKILL、INSTALL、SECURITY 和 `docs/architecture.svg`（有结构变化时）。
- 格式指纹会变的 PR（改了 `kernel/evolve.ts`、`kernel/schema.sql` 或卡片、轮次的字段），在 CHANGELOG 写“升级后第一次启动会重建视图”。

## 10. 完成定义

- 规则能检查、解释、预览、暂停、恢复、删除，删除前的预览和实际一致。
- 卡片能按规则选通道、按安静时段和紧急程度发送，回答者能按角色限定；旧的 `rules.json` 不用改。
- 参考客户端能跑，`/v1/state` 的字段有 Schema 和测试守着。
- 插件有版本、兼容声明和签名，安装和升级可追溯。
- 交付流水线在两个托管平台上通过同一套行为测试。
- 至少 3 个真实用户试用并给出反馈（修复计划 P2 的完成标准，不在代码里）。
